# طراحی: حساب کاربری، لندینگ عمومی و شخصی‌سازی کامل روزنگار

- تاریخ: ۲۰۲۶-۱۱-۰۱
- وضعیت: منتظر بازبینی مالک محصول
- دامنه: لایه‌ی احراز هویت، لندینگ عمومی، داده‌ی هر کاربر، تم‌ها، دسته‌ها و قالب هفتگی

## ۱. هدف

روزنگار از یک دفتر شخصیِ تک‌دستگاهی به یک اپ چندکاربره تبدیل می‌شود:

- هر کاربر با ایمیل خودش حساب بسازد یا وارد شود.
- کد تایید ۶ رقمی به ایمیل برسد.
- داده‌ی هر کاربر جدا و متعلق به خودش بماند.
- بدون ورود، فقط صفحه‌ی معرفی عمومی دیده شود.
- هر کاربر بتواند تم، دسته‌ها، بلوک‌های روز و بخش‌های اپ را برای حرفه‌ی خودش بسازد.
- اپ همچنان آفلاین کار کند و بعداً با اکانت همگام شود.

فلسفه‌ی «هر روز یک کار بزرگ» و «هیچ روزی صفر نیست» به‌عنوان تجربه‌ی پیش‌فرض می‌ماند، ولی دیگر به‌صورت سخت‌گیرانه بر کاربر تحمیل نمی‌شود؛ کاربر می‌تواند هر بلوکی را حذف یا جابه‌جا کند.

## ۲. تصمیم‌های معماری

### ۲.۱. میزبانی

- فرانت‌اند همچنان Next.js با `output: "export"` روی GitHub Pages می‌ماند.
- Supabase فقط برای احراز هویت و ذخیره‌ی ابری داده استفاده می‌شود.
- هیچ API Route سمت Next ساخته نمی‌شود.
- کلید `NEXT_PUBLIC_SUPABASE_ANON_KEY` عمومی است و امنیت با RLS تأمین می‌شود؛ کلید `service_role` هرگز در کلاینت یا ریپو نمی‌آید.

### ۲.۲. احراز هویت

Supabase Auth با سه جریان:

1. **کد یک‌بارمصرف**: `signInWithOtp` و سپس `verifyOtp({ type: "email" })`. اگر کاربر وجود نداشته باشد، ساخته می‌شود.
2. **رمز عبور + تایید ایمیل**: `signUp({ email, password })`، ارسال کد با قالب Confirm signup، تایید با `verifyOtp({ type: "signup" })`، ورودهای بعدی با `signInWithPassword`.
3. **بازیابی رمز**: `resetPasswordForEmail`، تایید کد با `verifyOtp({ type: "recovery" })`، تعیین رمز تازه با `updateUser({ password })`.

قالب‌های ایمیل Supabase باید شامل `{{ .Token }}` باشند:

- Magic Link: «کد ورود شما به روزنگار: {{ .Token }}»
- Confirm signup: «کد تایید حساب روزنگار: {{ .Token }}»
- Reset password: «کد بازیابی رمز روزنگار: {{ .Token }}»

کدها ۶ رقمی و کوتاه‌عمر هستند. دکمه‌ی ارسال دوباره ۶۰ ثانیه غیرفعال می‌شود.

### ۲.۳. مسیرها

| مسیر | دسترسی | توضیح |
| --- | --- | --- |
| `/` | عمومی | لندینگ تک‌صفحه‌ای |
| `/auth/` | عمومی | ورود، ثبت‌نام، تایید کد، بازیابی رمز |
| `/onboarding/` | نیازمند ورود | نام، الگوی حرفه، ریتم، تم |
| `/today/` | نیازمند ورود | نمای امروز |
| `/week/` | نیازمند ورود | هفته و باغ |
| `/progress/` | نیازمند ورود | پیشرفت |
| `/me/` | نیازمند ورود | حساب، ظاهر، ریتم، ماژول‌ها، داده |
| `/me/template/` | نیازمند ورود | ویرایش قالب هفتگی |
| `/me/categories/` | نیازمند ورود | مدیریت دسته‌ها |

- گروه مسیر `(public)` برای `/` و `/auth/` بدون پوسته‌ی اپ.
- گروه `(app)` برای مسیرهای برنامه با `AuthGuard` و `AppShell`.
- دسترسی بدون نشست به مسیرهای اپ → `/auth/?next=<path>`.
- لندینگ همیشه در `/` می‌ماند؛ برای کاربر واردشده دکمه‌ی «ادامه به امروز» نمایش داده می‌شود.
- `start_url` مانیفست به `./today/` تغییر می‌کند.

### ۲.۴. گیت و آفلاین

- `AuthGuard` ابتدا نشست محلی Supabase را می‌خواند.
- اگر نشست وجود داشته باشد ولی اینترنت قطع باشد، اپ با داده‌ی محلی باز می‌شود و وضعیت «آفلاین» نشان داده می‌شود.
- اگر نشستی نباشد، بدون توجه به کش، به `/auth/` هدایت می‌شود.
- Gate سمت کلاینت فقط UX است؛ محافظت واقعی داده RLS است.

`AppSettings` فعلی حفظ می‌شود تا تنظیمات موجود مهاجرت کنند. فیلدهای جدید با پیش‌فرض اضافه می‌شوند.

### ۳.۲. مهاجرت از نسخه‌ی ۱

- `schemaVersion: 1` تشخیص داده می‌شود و به ۲ تبدیل می‌شود.
- تنظیمات فعلی مستقیم map می‌شوند؛ `theme` حفظ می‌شود، `palette = "garden"`، `accent = "green"`.
- دسته‌های فعلی با همان idها به `categories` تبدیل می‌شوند و آیکون/رنگ می‌گیرند.
- `weekTemplate` از برنامه‌ی فعلی برای روزهای هفته ساخته می‌شود تا ظاهر و رفتار امروز تغییر نکند.
- `days`، `reviews`، `ideas`، `recoveries` بدون تغییر می‌مانند.
- مهاجرت در `migrateData()` خالص و تست‌پذیر است.
- JSON قدیمی (v1) از طریق «ورود داده» هنوز پذیرفته می‌شود.

### ۳.۳. ذخیره‌ی محلی

- کلید Zustand: `rooznegar-v2:<userId>`.
- کلید تم سراسری `rz-theme` حفظ می‌شود تا لندینگ و صفحه‌ی ورود هم تم درست داشته باشند.
- در اولین ورود، داده‌ی `rooznegar-v1` (بدون userId) خوانده و در صورت تأیید کاربر به حساب منتقل می‌شود.
- پس از خروج، داده‌ی همان کاربر روی دستگاه می‌ماند تا ورود آفلاین ممکن باشد؛ گزینه‌ی «خروج و پاک‌کردن داده‌های این دستگاه» هم وجود دارد.

### ۳.۴. ابر

```sql
create table public.planner_data (
  user_id uuid primary key references auth.users(id) on delete cascade,
  data jsonb not null,
  updated_at timestamptz not null default now()
);

alter table public.planner_data enable row level security;

create policy "read own data" on public.planner_data
  for select using (auth.uid() = user_id);

create policy "insert own data" on public.planner_data
  for insert with check (auth.uid() = user_id);

create policy "update own data" on public.planner_data
  for update using (auth.uid() = user_id)
  with check (auth.uid() = user_id);

create policy "delete own data" on public.planner_data
  for delete using (auth.uid() = user_id);
```

- هر کاربر یک ردیف دارد.
- داده‌ی کل اپ به‌صورت یک snapshot ذخیره می‌شود؛ برای حجم یک برنامه‌ریز شخصی مناسب است.
- `updated_at` سمت سرور با `now()` ست می‌شود.

## ۴. همگام‌سازی

### ۴.۱. قانون

- همه‌ی تغییرات اول محلی ذخیره می‌شوند.
- یک `dirty` flag و `updatedAt` در حافظه نگه داشته می‌شود.
- ۱.۵ ثانیه پس از آخرین تغییر، اگر نشست و اینترنت باشد، push انجام می‌شود.
- در ورود، بازگشت به تب، و آنلاین‌شدن، pull انجام می‌شود.
- تعارض: اگر `remote.data.updatedAt > local.updatedAt` باشد، نسخه‌ی ابری جایگزین می‌شود؛ در غیر این صورت نسخه‌ی محلی push می‌شود. این سیاست «آخرین تغییر برنده» است و برای اپ تک‌کاربره کافی است.
- اگر pull نسخه‌ی ابری را جایگزین کرد و کاربر در حال ویرایش بود، یک toast «نسخه‌ی جدیدتر از دستگاه دیگر آمد» نشان داده می‌شود.
- خطای شبکه هرگز مانع استفادهی محلی نمی‌شود.

### ۴.۲. وضعیت همگام‌سازی

در نوار بالا یک نشانگر کوچک:

- «همگام شد» با آیکون ابر/تیک
- «در انتظار» با نقطه‌ی نارنجی ملایم
- «آفلاین» با آیکون قطع
- «خطا · تلاش دوباره» با دکمه

### ۴.۳. تست‌های منطق

- ماتریس تصمیم pull/push برای چهار حالت: محلی تازه، ابری تازه، هر دو تازه، هیچ‌کدام.
- مهاجرت v1 → v2.
- حذف دسته‌ی استفاده‌شده در قالب.
- جابه‌جایی حالت دیر و بلوک‌های ثابت.

## ۵. لندینگ عمومی

### ۵.۱. ساختار

یک صفحه‌ی تک‌صفحه‌ای در `/` با این بخش‌ها:

1. **نوار بالا**: برند، لینک‌های «امکانات، تم‌ها، حریم خصوصی»، دکمه‌ی «ورود» و «شروع رایگان».
2. **هیرو**: وعده‌ی اصلی «هر روز، فقط یک کار بزرگ» + یک نمایش زنده‌ی کوچک از خط روز با خط «همین حالا».
3. **داستان روز**: سه ستون کوتاه: صبح، مسیر، شب؛ با تایپوگرافی متمایز.
4. **امکانات**: خط روز، هفته و باغ، مسیر CEFR، تایمر تمرکز، باشگاه، لینکدین، ژورنال، آفلاین.
5. **برای هر حرفه**: کارت‌های برنامه‌نویس، ورزشکار، خیاط، دانشجو و «دلخواه»؛ هر کارت نمونه‌ی یک روز را نشان می‌دهد.
6. **تم‌ها**: پیش‌نمایش شش پالت در دو حالت.
7. **حریم خصوصی**: داده‌ی هر کاربر جدا، RLS، ذخیره‌ی محلی، بدون فروش داده.
8. **سؤال‌های متداول** کوتاه.
9. **CTA پایانی** + فوتر.

- هیچ آمار ساختگی، نظر کاربر یا لوگوی جعلی استفاده نمی‌شود.
- اسکرین‌شات‌ها از نسخه‌ی واقعی گرفته می‌شوند.
- اگر کاربر وارد شده باشد، CTA به `/today/` می‌رود و نام/آواتار کوچک نمایش داده می‌شود.
- لندینگ هیچ داده‌ای از حساب کاربر نمی‌خواند.

### ۵.۲. هویت بصری

- همان زبان روزنگار: کرم، سبز مریم، آبی‌خاکستری، وزیرمتن، فضای سخاوتمندانه.
- لندینگ از پوسته‌ی اپ جدا است ولی همان توکن‌های رنگ و فونت را می‌گیرد.
- حرکت محدود و هدفمند: خط «همین حالا»ی زنده، ورود آرام بخش‌ها، پیش‌نمایش تم‌ها.
- بدون تصویر خارجی و بدون وابستگی سنگین.

## ۶. تم‌ها

### ۶.۱. پالت‌ها

هر پالت در روشن و تاریک تعریف می‌شود:

1. **باغ**: کرم و سبز مریم (پیش‌فرض فعلی)
2. **کاغذ**: کرم گرم، مرکب تیره، سبز زیتونی ملایم
3. **شب**: سبز-مشکی عمیق، نور مهتابی
4. **اقیانوس**: خاکستری-آبی، فیروزه‌ای آرام
5. **خاک رس**: خاکی گرم، سفال ملایم، بدون قرمز سرزنش‌گر
6. **آسمان**: آبی روشن، سفید شیری، آبی عمیق

- پیاده‌سازی با `data-palette` روی `<html>` و متغیرهای CSS.
- حالت روشن/تاریک همچنان با `data-theme`.
- انتخاب «همراه دستگاه» حفظ می‌شود.

### ۶.۲. رنگ تاکیدی

- گزینه‌ها: سبز، آبی، زیتونی، فیروزه‌ای، کهربایی.
- تاکید روی `--green`، `--green-deep`، `--green-soft`، `--green-wash`، `--btn-bg` اعمال می‌شود.
- هر ترکیب پالت/تاکید باید کنتراست متن دکمه ≥ 4.5:1 داشته باشد؛ در تست‌ها بررسی می‌شود.

### ۶.۳. انتخاب تم

- در `/me/` بخش «ظاهر»: انتخاب حالت، شش کارت پالت با پیش‌نمایش مینیاتوری، و پنج رنگ تاکیدی.
- تغییر فوری اعمال و ذخیره می‌شود.
- تم لندینگ و auth از تم ذخیره‌شده‌ی دستگاه استفاده می‌کند، حتی قبل از ورود.

## ۷. شخصی‌سازی محتوا

### ۷.۱. دسته‌ها

- هفت دسته‌ی فعلی با id ثابت می‌مانند تا ماژول‌های CEFR/لینکدین/باشگاه کار کنند.
- کاربر می‌تواند نام، نام کوتاه، آیکون و رنگ هر دسته را عوض کند.
- افزودن دسته‌ی دلخواه با id جدید.
- حذف دسته فقط وقتی مجاز است که در قالب استفاده نشده باشد یا کاربر مقصد انتقال بلوک‌ها را انتخاب کند.
- دسته‌های دارای ماژول تا وقتی ماژول روشن است حذف نمی‌شوند؛ اول ماژول خاموش می‌شود.
- ماژول‌ها:
  - CEFR به دسته‌ی `language` متصل است.
  - لینکدین به دسته‌ی `linkedin`.
  - باشگاه به دسته‌ی `gym`.
  - `programming` دسته‌ی رشد برای کار بزرگ عمیق است.
- دسته‌های دلخواه آمار عمومی (دقیقه و تعداد انجام) می‌گیرند.

### ۷.۲. قالب هفتگی

- برای هر روز هفته فهرست بلوک‌ها.
- افزودن، ویرایش، حذف و مرتب‌سازی بر اساس زمان.
- اعتبارسنجی: `end > start`، عدم هم‌پوشانی، عنوان غیرخالی.
- بلوک‌ها می‌توانند ثابت، قابل‌جابه‌جایی، قابل‌جبران و «کار بزرگ» باشند.
- حداکثر یک بلوک `core` پیش‌فرض در هر روز؛ کاربر می‌تواند در نمای امروز کار بزرگ را عوض کند.
- دکمه‌ی «بازگردانی به الگوی حرفه» با تأیید.
- الگوهای آماده:
  - **برنامه‌نویس**: بازتولید برنامه‌ی فعلی (کار، مسیر، زبان، برنامه‌نویسی عمیق، باشگاه، لینکدین، مرور پنجشنبه).
  - **ورزشکار**: تمرین صبح/عصر، تغذیه، ریکاوری، تمرین مهارت، خواب.
  - **خیاط**: کارگاه، سفارش‌ها، دوخت عمیق، بازار/تامین، استراحت، مرور.
  - **دانشجو**: دانشگاه، مطالعه، تمرین زبان، پروژه، استراحت.
  - **ساده**: بیداری، کار، یک بلوک رشد، استراحت، خواب.
- الگو فقط نقطه‌ی شروع است و همه‌چیز قابل ویرایش است.

### ۷.۳. برنامه‌ی روز

- موتور جدید `buildDaySchedule(dateKey, state)`:
  1. قالب همان روز هفته را برمی‌دارد.
  2. اگر حالت «دیر» فعال باشد، بلوک‌های `movable && !fixed` را به اندازه‌ی `lateShiftMinutes` جابه‌جا می‌کند.
  3. overrideهای همان تاریخ (انجام/رد/جبران) را اعمال می‌کند.
  4. کار بزرگ را از override روز یا `core` قالب انتخاب می‌کند.
  5. بلوک‌های قابل‌جبرانِ ردشده را به `recoverable` می‌برد.
- رابط خروجی `DaySchedule` حفظ می‌شود تا صفحه‌های امروز/هفته کمتر تغییر کنند.
- ردکردن بلوک‌های اصلی هم مجاز است؛ هیچ محافظ سختی وجود ندارد.
- قانون باغ:
  - `one`: حداقل یک بلوک انجام‌شده (پیش‌فرض)
  - `half`: نصف بلوک‌ها
  - `core`: کار بزرگ انجام شده
- سبک گل: خودکار بر اساس روز، یا انتخاب یکی از چهار حالت موجود.

### ۷.۴. ماژول‌ها

در `/me/`:

- CEFR، لینکدین، باشگاه، ژورنال، تایمر تمرکز، باغ، مرور هفتگی، یادآورها.
- خاموش‌کردن ماژول، کارت مربوطه را از امروز/پیشرفت/هفته حذف می‌کند ولی داده‌ی قبلی پاک نمی‌شود.
- مرور هفتگی حتی با نبود بلوک مرور، از صفحه‌ی هفته قابل بازکردن است.

### ۷.۵. اهداف

- هدف هفتگی زبان (دقیقه)، لینکدین (پست/کامنت)، باشگاه (جلسه) و سطح هدف CEFR.
- اهداف فقط وقتی ماژول روشن است نمایش داده می‌شوند.
- دسته‌های دلخواه هدف عددی اختصاصی ندارند؛ آمار عمومی دارند.

## ۸. صفحات و کامپوننت‌ها

### ۸.۱. احراز هویت

- یک صفحه با تب‌های «ورود» و «ساخت حساب».
- ورود: دو حالت «کد ایمیل» و «رمز عبور».
- ساخت حساب: ایمیل + رمز + تکرار رمز → کد تایید.
- ورودی کد ۶ خانه با paste و auto-advance.
- خطاها فارسی و دقیق؛ پیام‌های Supabase map می‌شوند.
- وضعیت بارگذاری، غیرفعال‌شدن دکمه، ارسال دوباره با شمارش معکوس.
- لینک «رمز را فراموش کردم».
- بعد از موفقیت: کاربر جدید → onboarding؛ کاربر قبلی → `next` یا `/today/`.

### ۸.۲. Onboarding

چهار گام کوتاه، قابل رد کردن بعد از گام الگو:

1. نام نمایشی و آواتار ایموجی اختیاری.
2. انتخاب حرفه/الگو.
3. ریتم: بیداری، شروع/پایان کار، خواب، روزهای کاری.
4. پالت و تاکید.

اگر داده‌ی v1 روی دستگاه باشد، قبل از گام ۲ پیشنهاد «داده‌های قبلی را به این حساب بیاور» نمایش داده می‌شود.

### ۸.۳. من

بخش‌ها:

- حساب: ایمیل، نام، آواتار، نشانگر همگام‌سازی، خروج، خروج و پاک‌کردن دستگاه.
- ظاهر: حالت، پالت، تاکید.
- ریتم: تنظیمات فعلی + روزهای کاری + حالت دیر.
- الگو: لینک به `/me/template/`.
- دسته‌ها: لینک به `/me/categories/`.
- ماژول‌ها: سوییچ‌ها.
- اهداف.
- داده: خروجی JSON v2، ورود JSON v1/v2، انتقال داده‌ی محلی، بازنشانی.
- حذف داده‌ی ابری (خودِ ردیف) با تایید دو مرحله‌ای.

### ۸.۴. AppShell

- مسیر `امروز` به `/today/`.
- برند به `/today/` (داخل اپ) و در لندینگ به `/`.
- نشانگر همگام‌سازی کنار تم.
- در حالت آفلاین، بنر کوتاه «آفلاین؛ تغییرات وقتی وصل شدی همگام می‌شوند».

## ۹. خطاها و حالت‌های مرزی

- Supabase پیکربندی نشده:
  - لندینگ کار می‌کند.
  - `/auth/` پیام «سرویس ورود هنوز وصل نشده» و راهنمای کوتاه نشان می‌دهد.
  - مسیرهای اپ باز نمی‌شوند.
- ایمیل تکراری، رمز کوتاه، کد اشتباه/منقضی، تلاش بیش از حد: پیام فارسی مشخص.
- قطع اینترنت هنگام ارسال کد: دکمه‌ی تلاش دوباره.
- نشست منقضی: خروج نرم به `/auth/` با پیام «دوباره وارد شو».
- همگام‌سازی ناموفق: داده‌ی محلی حفظ می‌شود و وضعیت «خطا» با تلاش دوباره.
- داده‌ی خراب در import: پیام «فایل معتبر نیست» و هیچ تغییری اعمال نمی‌شود.
- قالب دارای هم‌پوشانی: ذخیره با خطای مشخص جلوگیری می‌شود.
- حذف دسته‌ی در حال استفاده: انتخاب مقصد یا لغو.
- مرورگر بدون IndexedDB: همان fallback فعلی به localStorage.

## ۱۰. امنیت و حریم خصوصی

- فقط `anon key` در کلاینت؛ RLS مرز امنیتی است.
- هیچ کد/توکن تأییدی در لاگ یا localStorage توسط ما ذخیره نمی‌شود.
- رمز SMTP و `service_role` فقط در Supabase؛ هرگز در ریپو/ورک‌فلو/چت.
- `.env*.local` در `.gitignore`.
- در خروج، داده‌ی حافظه پاک می‌شود؛ پاک‌کردن کش محلی انتخابی است.
- حالت دموی احراز هویت فقط برای توسعه و با شرط `NODE_ENV !== "production"` و hostname محلی فعال می‌شود؛ در build تولیدی حتی با env اشتباه فعال نمی‌شود.
- تست منفی RLS: کاربر A نمی‌تواند ردیف کاربر B را بخواند/بنویسد.

## ۱۲. راه‌اندازی Supabase (پیش‌نیاز انتشار)

1. ساخت پروژه‌ی رایگان Supabase.
2. اجرای SQL جدول و چهار policy.
3. فعال‌کردن Email provider.
4. ویرایش سه قالب ایمیل با `{{ .Token }}`.
5. افزودن Custom SMTP (Brevo رایگان یا Gmail) برای ارسال به همه‌ی کاربران.
6. تنظیم Site URL و Redirect URLs روی `https://moeinparvizi.github.io/rooznegar/`.
7. قرار دادن `SUPABASE_URL` و `SUPABASE_ANON_KEY` در GitHub Actions Variables (نه Secrets، چون عمومی‌اند).
8. افزودن همان‌ها به `.env.local` برای توسعه.

تا قبل از این مراحل، نسخه‌ی گیت‌هاب فعلی دست‌نخورده می‌ماند تا کاربر از اپ قفل نشود. کار روی شاخه‌ی `feat/accounts` انجام و پس از تأیید QA merge می‌شود.
